# Bukti load test k6 (Sesi 29, 2026-09-16)

Perintah: `docker compose -f docker-compose.yml -f docker-compose.load.yml up -d` lalu `k6 run test/load/transfer.js` (API + Postgres 17 di Docker Desktop, Windows 11, satu laptop untuk klien dan server). Profil: 30 s naik ke 50 VU, 2 menit di 100 VU, 30 s turun. Setiap iterasi = 1 transfer Rp 10.000 + fee Rp 1.000 antar 50 dompet acak dengan Idempotency-Key baru; tanpa jeda antar iterasi (closed loop).

> Run pertama TANPA override gagal total secara sengaja-tidak-sengaja: rate limit login (5/15 menit per IP) dan transfer (20/menit per user) menolak 99,98 % request. Itu bukti pembatas bekerja, bukan angka latensi ledger — karena itu load test memakai override yang menaikkan batas.

## Analisis — SLO latensi TIDAK tercapai, correctness tercapai

| Target (docs/01 §7) | Hasil | Status |
|---|---|---|
| Ketepatan saldo 100 % | trial balance 0, drift 0, fee = 33.340 × Rp 1.000 persis | ✅ |
| Error rate < 1 % | 0,00 % dari 33.490 request | ✅ |
| Throughput ≥ 200 transfer/detik | **177/detik** | ❌ |
| p95 < 200 ms | **515 ms** | ❌ |
| p99 < 500 ms | **568 ms** | ❌ |

Penyebab yang teridentifikasi (belum diperbaiki, sengaja dicatat apa adanya):
1. **Baris panas `SYSTEM_FEE_REVENUE`.** Setiap transfer mengunci (`FOR UPDATE`) akun fee yang sama, sehingga semua transfer di seluruh sistem terserialisasi pada satu baris. Throughput maksimum ≈ 1 / (durasi commit satu transaksi). Ini keputusan desain Fase 1 yang benar untuk correctness tetapi menjadi pembatas skala.
2. **Lingkungan:** Postgres di Docker Desktop (Windows, WSL2) dengan `fsync` per commit; klien k6, API, dan DB berbagi satu laptop.
3. Kontensi tambahan: 100 VU closed-loop tanpa jeda memperebutkan hanya 50 dompet.

Perbaikan yang direncanakan (Fase 2, bukan sekarang): (a) fee tidak dicatat ke satu akun global per transaksi, melainkan ke N sub-akun fee (sharding) atau diakumulasi per periode; (b) uji ulang di Linux native / server dengan disk cepat; (c) `synchronous_commit=off` hanya untuk mengukur batas atas (bukan untuk produksi ledger).
